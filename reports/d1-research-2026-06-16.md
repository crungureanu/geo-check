## 1. Confirmed limits / facts (each with doc URL + date checked)

### 1.1 D1 platform limits

Source: <https://developers.cloudflare.com/d1/platform/limits/> — checked 2026-06-16.

| Limit | Free | Workers Paid |
| --- | --- | --- |
| Databases per account | 10 | 50,000 |
| Max database size | 500 MB | 10 GB |
| Storage per account | 5 GB | 1 TB |
| Max columns per table | 100 | 100 |
| Max rows per table | Unlimited (bounded only by DB size) | same |
| Max string / BLOB / row size | 2,000,000 bytes (2 MB) | same |
| Bound parameters per query | 100 | 100 |
| Max SQL statement length | 100,000 bytes (100 KB) | same |
| Max query duration | 30 seconds | same |
| **Queries per Worker invocation** | **50** | **1,000** |
| Time Travel (point-in-time recovery) | 7 days | 30 days |

Notes that matter for us:
- **"Queries per Worker invocation" is a D1-specific limit (50 free / 1,000
  paid), separate from the general Workers subrequest cap below.** The D1 limits
  page lists it explicitly. This is the real ceiling on how many `.prepare().run()`
  calls a single Function invocation may issue. The admin must stay well under
  1,000 D1 queries per load. Our redesigned admin uses a handful of indexed
  queries, so this is a non-issue, but it is the number to size against (not the
  subrequest cap).
- **Bound parameters per query = 100.** A bulk backfill that builds one big
  multi-row `INSERT ... VALUES (?,?,...),(?,?...)` must chunk so total `?`
  placeholders stay <= 100. With ~11 columns per `scans` row that is <= 9 rows per
  statement. Use `batch()` of single-row inserts instead (cleaner; see 1.4).
- Max columns = 100. The `scans` table in the plan has ~15 columns. Fine.

### 1.2 Workers subrequest limit (the thing that was blamed for Error 1101)

Source: <https://developers.cloudflare.com/changelog/post/2026-02-11-subrequests-limit/>
and <https://developers.cloudflare.com/workers/platform/limits/> — checked 2026-06-16.

- As of **2026-02-11**, Workers Paid is **no longer capped at 1,000 subrequests
  per invocation**. New default = **10,000 subrequests / invocation**, configurable
  up to **10,000,000** via `limits` in Wrangler config.
- Workers Free stays at **50 external subrequests + 1,000 subrequests to
  Cloudflare services** (KV/D1/R2 count as Cloudflare-service subrequests).
- A subrequest = any `fetch()` or any call to a Cloudflare service (KV, D1, R2).
  So D1 queries count toward BOTH the D1 "1,000 queries/invocation" limit AND the
  general subrequest budget. On Paid the binding constraint is the D1-specific
  1,000, not the 10,000 subrequest cap.

**This confirms the 2026-06-16 correction already in `data-layer-redesign-plan.md`
§1**: the old admin's ~2,300 KV reads were UNDER the 10,000 subrequest cap on
Paid, so a cap breach did not cause the 1101. The 1101 was an uncaught exception
and/or CPU/wall-clock timeout from doing thousands of sequential KV reads. The
existing plan is correct on this point.

### 1.3 D1 pricing (for the cost model)

Source: <https://developers.cloudflare.com/d1/platform/pricing/> — checked 2026-06-16.

| | Free | Workers Paid |
| --- | --- | --- |
| Rows read | 5 million / day | First 25 billion / month, then $0.001 / million |
| Rows written | 100,000 / day | First 50 million / month, then $1.00 / million |
| Storage | 5 GB total | First 5 GB, then $0.75 / GB-month |

D1 bills on **rows read / rows written**, not on queries. An indexed
`SELECT ... LIMIT 50` reads ~50 rows, not the whole table (that is the entire
point of moving the admin off KV).

### 1.4 Query API (Functions / Workers) — behaviour and gotchas

Sources: <https://developers.cloudflare.com/d1/worker-api/d1-database/> and
<https://developers.cloudflare.com/d1/worker-api/prepared-statements/> — checked
2026-06-16.

- `env.DB.prepare(sql)` -> prepared statement; `.bind(...)` fills `?` placeholders
  (ordered or named). Always parameterise; never string-concat user input.
- `.first()` returns the first row object, or **`null` when no row matches**.
  `.first("col")` returns just that column's value; **throws `D1_ERROR` if the
  column does not exist** but rows do. Append `LIMIT 1` for performance (it does
  not add one for you).
- `.run()` is an **alias of `.all()`**. Both return a `D1Result`:
  `{ success, meta, results }`. **`results` is empty `[]` for `INSERT`/`UPDATE`/
  `DELETE`** (unless you add a `RETURNING` clause). The write outcome is in
  `meta` (`changes`, `last_row_id`, `rows_written`, `rows_read`, `duration`).
  Gotcha: do not check `result.results.length` to confirm a write happened; check
  `meta.changes`.
- `.batch([stmt, stmt, ...])` sends multiple prepared statements in ONE call.
  **Batched statements are a SQL transaction**: they execute sequentially,
  non-concurrently, in auto-commit; **if any statement fails the whole batch
  rolls back**. This is the only transaction primitive D1 gives in a Function.
- **No interactive transactions.** There is no `BEGIN`/`COMMIT` you can hold open
  across `await`s. Anything that must be atomic has to fit in one `batch()`.
  Implication for us: a dual-write where we write KV then D1 is NOT atomic across
  the two stores (different systems) — design each side to be independently
  fail-soft (it already is for KV; do the same for D1).

### 1.5 Read replication / Sessions API — status and relevance

Source: <https://developers.cloudflare.com/d1/best-practices/read-replication/>
and <https://developers.cloudflare.com/d1/configuration/data-location/> — checked
2026-06-16.

- Read replication distributes read-only copies of the DB globally. Enabled per
  database: Dashboard -> D1 -> database -> **Settings -> Enable Read Replication**,
  or REST API `read_replication: { mode: "auto" }`.
- The **Sessions API** (`db.withSession(constraint)`) gives sequential
  consistency across replicas via **bookmarks**. Constraints: `"first-unconstrained"`
  (route first query anywhere), `"first-primary"` (route to primary for freshest
  data), or a bookmark string.
- **Pricing: no extra storage/compute cost** for replicas; you pay standard
  rows-read/written either way.
- **Relevance to us: low / defer.** Our write and read volumes (10–5,000
  scans/day) are tiny; the primary instance handles this with room to spare.
  Read replication helps global read latency and high read throughput, neither of
  which is a current bottleneck. It also adds eventual-consistency edge cases
  (stale reads right after a write) that complicate the admin and dual-write.
  **Recommendation: leave read replication OFF for v1; revisit only if admin read
  latency from distant regions becomes a real complaint.** If enabled later,
  admin reads can stay default-routed; write-then-read paths (rare here) would
  need `first-primary` or a bookmark.

### 1.6 Cost / limit model at 10–5,000 scans/day: is D1 or KV the constraint?

At the planned dual-write volume, **per the redesign one scan becomes ~1 KV write
(share blob) + a few D1 writes** (1 `scans` row; +1 `unlock_leads`/`connections`
on unlock; a later `UPDATE` on speed).

Worst case 5,000 scans/day, generously assume ~4 D1 row-writes per scan:
- D1 writes: 5,000 × 4 × 30 = **600,000 rows written / month**. Paid includes
  50,000,000/month. Headroom ~80×. Cost: $0.
- D1 reads: admin viewed even 2,000×/day at ~300 rows/load = 600k rows read/day =
  ~18M/month, vs 25,000,000,000 included. Effectively $0.
- D1 storage: a `scans` row is tiny (~200 bytes). 5,000/day × 365 = ~1.8M rows/yr
  ≈ a few hundred MB. Well under the 5 GB included and the 10 GB DB cap.
- KV writes drop from ~5/scan to ~1/scan: 5,000/day × 30 = 150,000 writes/month,
  vs 1,000,000 included on Paid. Comfortable.

**Conclusion: neither D1 nor KV is the binding constraint at 5,000 scans/day on
Workers Paid.** The original incident was the **Free-tier KV daily caps**
(100k reads / 1k writes per UTC day), which the account already escaped by moving
to Paid. D1's relevant per-invocation ceiling (1,000 queries) is a design rule,
not a volume limit. The real wins from D1 are correctness (atomic counters, no
lost updates) and killing the admin fan-out, not cost.

## 2. Recommended binding + migration setup (preview AND production)

### 2.1 The key project-specific fact: this Pages project has NO wrangler config

There is no `wrangler.toml`/`.jsonc` in the repo, and `migrations/` does not
exist. The project is **Pages, configured via the dashboard** (KV `SHARES` is
bound in the dashboard, per the memory notes about per-env bindings). That shapes
the recommendation: you can go **dashboard-only** for the binding, and use
Wrangler **purely as a migration CLI** pointed at the database by name, without
adopting a full wrangler-managed config.

Two viable setups:

**Option A (recommended): dashboard bindings + Wrangler-CLI-only for migrations.**
- Bind D1 to the Pages project in the dashboard for BOTH Preview and Production
  (per-environment, like `SHARES` already is — see §5 steps).
- Keep migrations as `.sql` files in `migrations/` and apply them with
  `wrangler d1 migrations apply <DB_NAME> --remote`, targeting the database by
  **name** (no project wrangler config needed for `d1 execute`/`migrations apply`
  when you pass the DB name and `--remote`). This matches the project's
  "wrangler-free deploy, dashboard-managed" style: Wrangler is only a schema tool,
  never in the deploy path.

**Option B: adopt a minimal Pages `wrangler.jsonc`.** Cleaner per-env binding in
code, but it means the binding now lives in a config file the deploy reads, which
is a bigger change to the current dashboard-managed model. Only do this if you
later want bindings in version control. If chosen, the Pages-specific rules are:
- Top-level `[[d1_databases]]` applies to **local dev + production**.
- `[env.preview]` overrides for **preview** deployments.
- For Pages, **only `preview` and `production` env names are allowed** under
  `[env.<name>]` (unlike Workers).
- `d1_databases` is a **non-inheritable key**: if you override it for `preview`,
  you must re-specify the full binding in that env block (it does not merge).

Pages wrangler D1 syntax (Option B, for reference):
```toml
# wrangler.toml (Pages)
name = "geo-check"
pages_build_output_dir = "<output dir>"

[[d1_databases]]
binding = "DB"
database_name = "xeoscan-prod"
database_id = "<PROD_DATABASE_ID>"

[[env.preview.d1_databases]]
binding = "DB"
database_name = "xeoscan-preview"
database_id = "<PREVIEW_DATABASE_ID>"
```
Source for all Pages-binding rules:
<https://developers.cloudflare.com/pages/functions/wrangler-configuration/> and
<https://developers.cloudflare.com/pages/functions/bindings/> — checked 2026-06-16.

### 2.2 Two databases or one?

Use **two separate D1 databases** (`xeoscan-preview`, `xeoscan-prod`), bound to
the same variable name `DB` in each environment. This mirrors how Preview and
Production KV are scoped separately (a repeatedly-bitten lesson in this repo).
A migration applied to preview never touches prod data, and you can test schema
changes safely. Paid allows 50,000 DBs, so two is free of any limit pressure.

### 2.3 Migration workflow (commands)

Sources: <https://developers.cloudflare.com/d1/reference/migrations/> and
<https://developers.cloudflare.com/d1/wrangler-commands/> — checked 2026-06-16.

```bash
# one-time: create the two databases (copy the database_id each prints)
npx wrangler d1 create xeoscan-preview
npx wrangler d1 create xeoscan-prod

# scaffold a migration file under ./migrations
npx wrangler d1 migrations create xeoscan-prod 0001_initial_schema

# ...edit migrations/0001_initial_schema.sql...

# apply to PREVIEW database first (verify), then PROD
npx wrangler d1 migrations apply xeoscan-preview --remote
npx wrangler d1 migrations apply xeoscan-prod    --remote

# inspect / ad-hoc query a remote DB
npx wrangler d1 execute xeoscan-prod --remote --command "SELECT COUNT(*) FROM scans;"
```
Gotchas confirmed in docs:
- `wrangler d1 migrations apply` **prompts for confirmation** and **captures an
  automatic backup** before applying to a remote DB.
- `--remote` targets the live (production-class) D1 database; `--local` hits the
  local Miniflare copy used by `wrangler pages dev`. There is also a separate
  `--preview` flag that targets a project's *preview* D1 binding — but that flag
  is for wrangler-config-managed preview bindings (Option B). With **Option A** we
  address preview vs prod by **passing the explicit database name** (
  `xeoscan-preview` vs `xeoscan-prod`) with `--remote`, which avoids any ambiguity
  about which DB a flag resolves to. Cloudflare's own guidance: prefer the DB
  **name** (immutable) over the binding name (mutable) to avoid migrating the
  wrong target.
- On this Windows machine, `npx wrangler` may need `NODE_OPTIONS=--use-system-ca`
  (per the repo's Node TLS memory note) for the remote API call to succeed.

### 2.4 Local dev

`npx wrangler pages dev <output_dir> --d1 DB=xeoscan-preview` binds D1 locally;
`wrangler d1 migrations apply xeoscan-preview --local` seeds the local copy. Local
and remote D1 are independent stores.

## 3. Corrections to `data-layer-redesign-plan.md`

The plan is largely sound and already self-corrected the subrequest myth. Items
to flag:

1. **WRONG NUMBER — subrequest cap in `scaling-hardening-plan.md` §2/§3.** That
   older doc still says "Workers Paid subrequest limit is **1,000 per request**"
   and "exceeds the Workers subrequest limit (50 free / 1,000 paid) -> Error 1101."
   That is outdated: since 2026-02-11 Paid defaults to **10,000** (configurable to
   10M). `data-layer-redesign-plan.md` §1 already corrects this; the hardening doc
   should carry a pointer or a one-line correction so the stale 1,000 figure is
   not used for sizing. The fix (cut the fan-out) is unchanged.

2. **CLARIFY — the real D1 ceiling for the admin is "1,000 D1 QUERIES per
   invocation", not the subrequest cap.** The plan reasons in subrequests; for the
   D1-backed admin the tighter, D1-specific number is 1,000 queries/invocation
   (Paid). The redesigned admin (a few indexed `SELECT`s) is far under this, so no
   change is needed, but §4/§9 should size against the D1 query limit, not the
   10,000 subrequest budget, to avoid a future N-queries-in-a-loop regression.

3. **RISKY — bound-parameter limit (100) for the backfill.** Plan §10 step 3
   backfills KV rows into D1. A naive multi-row `INSERT` will blow the **100 bound
   parameters per query** limit fast (~9 rows at 11 columns). Use `db.batch()` of
   single-row prepared statements, chunked (e.g. 50–100 statements per batch), and
   remember a batch is one transaction that rolls back wholesale on any failure —
   so make each row's insert `INSERT ... ON CONFLICT(share_id) DO NOTHING` (the
   plan already specifies this) and keep batches modest so one bad row does not
   roll back hundreds. Add this constraint to §3/§10.

4. **CONFIRM — `.run()`/`.all()` write-result gotcha for dual-write.** Plan §10
   step 2's deferred speed `UPDATE ... WHERE share_id=?` "no-ops gracefully when
   the row is absent." Correct, but note the verification detail: a no-match
   `UPDATE` still returns `success: true` with an **empty `results`** and
   `meta.changes = 0`. If any code wants to know whether the speed row landed, it
   must read `meta.changes`, not `results.length`. Worth a one-line note in §10.

5. **OK / endorse — KV stays for share blobs + rate windows; D1 for tabular.**
   Correct split. Confirmed: KV is right for key-by-id 7-day blobs; D1 is right for
   counted/queried/joined data. No change.

6. **OK / endorse — atomic counters via SQL.** `SELECT COUNT(*), SUM(pages)` for
   lifetime totals, and atomic `UPDATE scans SET visits = visits + 1` for the
   visit counter, both kill the read-modify-write races. Confirmed feasible: a
   single `UPDATE ... SET col = col + 1` is atomic within D1's auto-commit. Good.

7. **MINOR — read replication is mentioned implicitly via "edge cache" but not
   D1 replication.** Recommend the plan explicitly state read replication is
   **deferred/off for v1** (see §1.5 here) so it is a conscious decision, not an
   omission, when someone later sees the dashboard toggle.

8. **NOTE — no interactive transactions.** The plan's dual-write is inherently
   non-atomic across KV and D1 (two systems). That is fine given both sides are
   fail-soft, but the plan should state it so nobody later expects a rollback to
   span both stores. Within D1, multi-table atomic writes (e.g. insert lead +
   upsert connection) must go through a single `batch()`.

Nothing in the plan is dangerously wrong. The two things to actually change are
the **stale 1,000-subrequest figure in the hardening doc** and adding the
**100-bound-param / batch** constraint to the backfill section.

## 4. Dual-write (KV + D1) scaffold: file-by-file checklist (behind a DISABLED flag)

Goal: land all the D1 plumbing on `main` with the binding ABSENT and a flag OFF,
so it is a pure no-op until you (a) create + bind the DB and (b) flip the flag.
Every D1 call is fail-soft and guarded by `isD1Enabled(env)`, so a missing `DB`
binding or a thrown D1 error can never affect a user-facing scan.

**Flag/guard contract:** D1 is "on" only when BOTH the binding exists AND an env
var opts in. Suggested guard:
```ts
// in the new d1 module
export function d1(env: { DB?: D1Database; D1_ENABLED?: string }): D1Database | null {
  if (!env.DB) return null;                 // no binding -> off
  if ((env.D1_ENABLED || "") !== "1") return null; // flag off -> off
  return env.DB;
}
```
This means: ship now (no binding, no var) = nothing happens. Later, bind `DB` and
set `D1_ENABLED=1` on Preview, verify, then on Production.

checklist (scan, speed, unlock, admin) -> verify rows land in D1 via
`wrangler d1 execute ... --remote` -> bind+migrate Prod -> flip Prod flag ->
backfill -> cut admin reads -> retire KV tabular writes. Each step independently
reversible: flipping `D1_ENABLED` back to `0` instantly returns to KV-only.

## 5. Manual Cloudflare dashboard steps (the user must do these)

These cannot be done from code and must be done by the account owner. None of
them affect production until the final flag flip.

1. **Create two D1 databases** (CLI or dashboard):
   - `npx wrangler d1 create xeoscan-preview`
   - `npx wrangler d1 create xeoscan-prod`
   - Record each `database_id`. (On this machine prefix with
     `NODE_OPTIONS=--use-system-ca` if the API call fails on certs.)
2. **Apply the schema migration to each** (preview first):
   - `npx wrangler d1 migrations apply xeoscan-preview --remote`
   - `npx wrangler d1 migrations apply xeoscan-prod --remote`
   - Confirm the prompt; Cloudflare auto-backs-up before applying.
3. **Bind D1 to the Pages project, PER ENVIRONMENT** (dashboard):
   - Workers & Pages -> `geo-check` -> Settings -> Bindings -> Add -> D1 database.
   - Variable name: **`DB`**. Select `xeoscan-preview` for the **Preview**
     environment binding and `xeoscan-prod` for the **Production** environment
     binding. (Pages scopes bindings per environment exactly like the existing
     `SHARES` KV binding — set BOTH; a missing prod binding silently no-ops.)
   - Redeploy after adding (Pages requires a redeploy for new bindings to take).
4. **Set the enable flag, per environment** (dashboard -> Settings -> Variables
   and Secrets, or env vars):
   - Add `D1_ENABLED = 1` to **Preview** first. Verify with the §1 preview
     checklist + a `wrangler d1 execute xeoscan-preview --remote --command
     "SELECT COUNT(*) FROM scans;"` to confirm rows are landing.
   - Only after preview is clean, add `D1_ENABLED = 1` to **Production**.
5. **(Deferred, optional) Read replication:** leave the **Enable Read
   Replication** toggle OFF for v1 (D1 page -> database -> Settings). Revisit only
   if global admin read latency becomes a real issue (see §1.5).
6. **(Deferred) Cloudflare Access on `/admin`** per the plan — independent of D1,
   not required for the scaffold.
